### 注意事项

* 使用的数据表名变更为 `_access` （移除了 _log 后缀），可手动修改表名；
* 升级插件请请先禁用插件后更新，待更新完毕后重新启动插件，数据可自动恢复（视设置而定）；
* 插件所在目标名必须为 `Access` 否则可能出现玄学问题；
* 因 IPv6 支持问题，使用了 `gmp` 函数，需要安装 `php_gmp` 插件（因不同环境的部署方式不同，因此在此不再赘述）；
* 因新版弃用了本地数据库，因此 IP 查询可能影响速度会变慢，如果出现英文结果是因为当前网络环境不佳，访问 IPIP 的接口失败，因此使用了备用的接口，此功能需要 `php_curl` 插件支持（暂不支持 IPv6 地址归属地查询）；
* ip 字段存的是地址的**十进制整数表示**（IPv4 走 `ip2long`，IPv6 走 `gmp` 换算），不是地址文本。上限由 `2^128-1` 的位数决定，即 39 位：
  * 早期版本按 38 处理，而十进制数截掉末位等于除以 10，所以 `fc00::/7`、`fe80::/10`、`ff00::/8` 这些恰好 39 位的地址会被存成**另一个看起来合法的地址**。`2000::/3` 全球单播是 38 位，一直没事，这也是它长期没被发现的原因（反代或局域网下 `REMOTE_ADDR` 是 `fe80::` 很常见）；
  * v3.2.1 的结构升级会自动把 MySQL 存量表的 ip 列扩为 `char(39)`；PostgreSQL 建表脚本一直是 `varchar(39)`，SQLite 不强制字符长度，两者都不需要动；
  * **MySQL 大表请挑低峰升级**：改 CHAR 长度只能走 `ALGORITHM=COPY`，会把整表连同全部索引一起重建并阻塞写入。升级只在探测到列宽不够时才执行，已经够宽的表不会被重建；
  * **升级后请尽快重新启用一次插件（或保存一次设置）**。在「插件文件已经换掉、结构升级还没跑」的窗口里，上述地址会被 MySQL 严格模式拒绝，转入死信队列而不是写进统计表——数据不会丢，但 `flush-queue.php` 会以 1 退出提醒你。
* **PostgreSQL 用户注意**：建表脚本会给 ip 列固定 `n_distinct = -0.1` 的估计，结构升级也会给存量表补上：
  * `ANALYZE` 是从三万行样本外推 `n_distinct` 的，对高基数列出了名地不准。实测一张 314 万行的表真实有 45 万个不同 ip（14.3%），却被估成 22,878（0.73%）—— 低估 20 倍；
  * 后果不是「差一点」而是**选错计划**：规划器按两万多组去规划哈希表，实际要装四十几万组，超出 `work_mem` 后 HashAggregate 落盘重分区。概览页那条「总计独立 IP」因此跑了 **643 秒**，控制台稳定 504。估对之后改走「按 `(ip, ua)` 索引顺序相邻去重」，不建哈希表，耗时 **1 秒**；
  * 取值方向比精度重要：估低了要落盘、慢几百倍，估高了只是多读点索引、有上界，两者代价不对等，所以宁可往高取。想调准可以自己量一次 `SELECT count(DISTINCT ip)::float / count(*) FROM [前缀]access;` 再改；
  * 这个设置**重建表就会丢失，而且毫无征兆**（不影响正确性，只是某条查询悄悄慢几百倍），所以它和 event_id 唯一索引一样被纳入了每次启用的实地校验。
* 需要 PHP 8.2 或更高版本（启用插件时会检查，不满足直接拒绝启用）；
* 需要 PHP cURL、intl、mbstring、GMP 扩展，以及 64 位 PHP（启用插件时会逐项检查，不满足直接拒绝启用）；
* 支持 MySQL / MariaDB、SQLite 和 PostgreSQL 三种数据库，建表脚本分别位于 `sql/MySQL.sql`、`sql/SQLite.sql` 和 `sql/PostgreSQL.sql`，启用插件时会按当前适配器自动选择；
* 统计数据默认与 Typecho 共用一个库，也可以在插件设置里单独指定一个 MySQL / PostgreSQL 连接（地址、端口、用户名、密码、库名、表前缀），把访问日志与博客数据分开存放：
  * 目标数据库需要提前创建好，插件只负责建表；保存设置时会先测试连接，连不上则不保存；
  * 切换到独立数据库时会把主库中已有的统计数据迁移过去，不超过 5 万行在保存设置时直接完成；
  * 数据量更大时提供两种方式，都用 keyset 分页 + 批量写入，都支持断点续传：
    * **统计控制台**：页面顶部会出现迁移进度条，点「开始迁移」即可，浏览器分片调用后台接口，每片约 3 秒，不受 Web 超时限制，也不需要服务器 SSH 权限（实测速度与命令行基本持平）；
    * **命令行脚本**：`php usr/plugins/Access/tools/migrate.php`，适合超大表或想挂到计划任务里跑；支持 `--dry-run`、`--batch=N`、`--yes`、`--root=`；
  * 迁移未完成时后台会明确显示剩余行数，不会把截断当成成功；暂停、关页面、断线之后回到控制台或重跑脚本都会从断点继续；
  * 从 3.0.x 升级上来的站点，需要在插件管理里禁用并重新启用一次 Access，才能注册迁移接口（控制台会提示）；
  * 独立库无法与 `typecho_contents` 做 JOIN，文章标题改为回主库二次查询后在 PHP 中合并，功能与共用一个库时一致；
  * 若独立库临时不可用，只会导致这次访问不被统计，不影响博客本身的访问。
* 配置了 Redis（即启用「缓存加速」）时，会自动启用**写入队列**：访问日志先进 Redis 列表，攒够一批再用一条多值 INSERT 落库：
  * 目的是削掉每次访问的建连接开销，并把数据库连接数从「每次访问一条」降到「每批一条」，避免突发流量打满 `max_connections`；
  * 实测（独立 PostgreSQL，每个请求独立进程）：直写 4.67 ms/次访问，队列 0.12 ms/次访问；
  * 刷库由访问请求顺带触发，且推迟到响应发出之后执行（PHP-FPM 下用 `fastcgi_finish_request`），承担刷库的访客感知不到延迟；
  * 打开统计控制台时会先同步刷一次，保证看到的数字不滞后；低流量站点可把 `tools/flush-queue.php` 挂到 cron 兜底：
    `* * * * * cd /path/to/typecho && php usr/plugins/Access/tools/flush-queue.php --quiet`
  * 数据库写不进去时队列不会被裁剪，数据留到下次重试；队列上限 20 万条，超出后丢弃最旧的记录；
  * 没有配置 Redis、Redis 连不上、或在设置里把「写入队列」设为禁用时，写入行为与之前完全一致（直接 INSERT）。
* **启用写入队列之后，Redis 不再只是「删了会重算」的缓存**，它同时装着还没落库的访问日志。请按数据存储来配置它：
  * **必须开启持久化**：`appendonly yes`，并把 `appendfsync` 设为 `everysec`（默认）或 `always`。
    只用 RDB 的话，两次快照之间的写入在 Redis 重启后会全部消失 —— 那就是一段时间的访问日志凭空不见；
  * **不要给这个 Redis 配会淘汰队列键的 `maxmemory-policy`**。`allkeys-lru` / `allkeys-random` 会在内存吃紧时
    连队列一起淘汰，而且不留任何痕迹。要限内存就用 `volatile-lru` 一类只动带 TTL 的键的策略
    （队列、死信、processing 都不设 TTL，只有统计缓存设），或者干脆 `noeviction`；
  * **数据丢失窗口**：`appendfsync everysec` 下 Redis 进程被强杀最多丢最近 1 秒的写入；
    主从架构下故障切换会丢掉尚未复制到从库的那部分。介意的话就把刷库阈值调小
    （`queueFlushSize` / `queueFlushInterval`），让数据更快落到数据库里；
  * **只支持单节点（standalone）Redis，不支持 Redis Cluster**。取批次用的 Lua 脚本会同时操作
    `...:queue` 和 `...:queue:processing` 两个键，它们没有 hash tag，在 Cluster 上会直接报 `CROSSSLOT`。
    Sentinel 后面挂一个可写地址是可以的，但要接受上面说的切换丢数据窗口；
  * 停用插件时会先尽力把队列刷干净；刷不干净且没有勾选「删除数据表」时，队列和死信原样保留，下次启用继续。
* **Redis 键名带站点指纹**（`plugin:access:{12 位指纹}:...`，指纹取自插件目录路径），
  同一台机器上的多个 Typecho 共用一个 Redis DB 时不会再串队列、串锁、串缓存：
  * 键名前缀在 v3.2.3 从 `typecho_access:` 换成了 `plugin:access:`，与本站其他插件
    （如 Accelerate 的 `plugin:accelerate:`）统一。**换前缀这一步不做接管**：
    升级前请先把队列刷干净 —— 跑一次 `tools/flush-queue.php`，或者在后台禁用一次插件 ——
    否则 `typecho_access:{指纹}:queue` 里没落库的消息会滞留在旧键上无人消费；
  * 更早的、加指纹之前的老键（`typecho_access:queue` 等）仍会自动接管：
    **保存一次插件设置**、或者让 `tools/flush-queue.php` 跑一次即可；
  * 多个站点共用一个插件目录（软链、共享代码）时指纹相同，仍然会串。这种部署请给每个站点配不同的 Redis 实例；
  * 卸载清理会把 `plugin:access:*` 和 `typecho_access:*` 两个前缀都扫一遍，但只删本站点指纹下的键
    和加指纹之前遗留的老键，不会碰同一个 Redis 上别的站点。
* **改动会让队列换主人的设置时，队列必须先刷干净**。Redis 地址/端口/密码、「写入缓冲」开关、
  统计数据库的类型/地址/库名/表前缀，任何一项变了都意味着已经攒在队列里的消息将无人认领：
  换了 Redis 就是够不着，只换库则是被写进错误的库。所以这时插件会先用**旧配置**把队列刷完，
  刷不干净就**拒绝保存**并说明原因。确认可以丢下这些消息时，把设置里的「队列归属变更」改成
  「强制切换一次」再保存 —— 它只对这一次保存生效，之后自动复位。
* **不带时间范围的全表聚合**（总计三个数字、来源 Top N、文章饼图）单独按一套规则缓存：
  * 覆盖索引只对带时间范围的查询有效，这几项没有 `WHERE`，代价随数据量线性增长且没有上界；
  * 采用**陈旧优先**：缓存过期时先把旧值返回，重算挂到响应发出之后（`fastcgi_finish_request`）做，看的人一秒都不用等；
  * **冷缓存时不当场算**，接口回 `done=false`，前端隔两秒再问一次。一条没有上界的查询很可能比 nginx 的 `fastcgi_read_timeout` 还久，那时浏览器已经 504、PHP 却还在磨，刷新几次就能把 PHP-FPM 的 worker 堆满；
  * 重算带互斥标记，前端反复轮询也只会有一条在跑；算失败时标记留到自然过期，充当失败退避；
  * 队列刷库**不再删除**这几项的缓存 —— 新写入的几条访问对「总计」只是个零头。按日期的键仍然照常失效，那是为了修跨零点后前一天数字不更新的问题。
* **来源统计会自动滤掉「不是来源地址」的值**。Referer 头完全由对方控制，扫描器每天往里塞 SQL 注入探测串，它们会被当成一次来源记下来，而且因为被反复刷、次数很高，正好占着 Top 20 的前排：
  * 判定用**白名单**而不是黑名单——黑名单在这件事上必然失败，payload 的花样是无穷的，而且拿 `sleep`/`select`/`union` 这类关键词去匹配，迟早会误伤查询串里带这些词的正常地址。真正该问的从来不是「它像不像攻击」，而是「它是不是一个来源地址」：带 scheme 和主机名、中间没有空白字符的绝对 `http(s)` URL；
  * 写入侧和读取侧各挡一次。写入侧顺带解决了一个放大效应：`entrypoint` 会被写进 cookie，不拦的话一条 payload 会被那个客户端的后续每一次请求反复带回来；
  * 读取侧的过滤放在 SQL 里而不是取回 PHP 再筛——Top N 是数据库排序取前几名的，先取二十条再筛可能只剩几条；
  * 单条日志的 `referer` 字段**不做改写**，原样保留（日志页只把 `http(s)` 的渲染成链接，其余按纯文本显示），这样排查时还看得见对方发了什么。
* **控制台是前端渲染的，接口只给原始数据，转义由渲染层负责**。服务端不要再对 JSON 返回值做 HTML 转义，转两遍会让页面显示出 `&#039;` 这类字面量。日志页的「来源」只有 `http(s)://` 才渲染成链接，其余按纯文本显示 —— Referer 头完全由对方控制，`javascript:` 这类伪协议靠转义是拦不住的。
* 数据量大（几十万行以上）时的概览页优化：
  * 概览的三个数字都是按时间范围聚合的：PV 是 `COUNT(*)`，IP 是 `COUNT(DISTINCT ip)`，UV 是 `COUNT(DISTINCT ip, ua)`。
    只有 `time` 单列索引时，后两个要按 time 找到行再回表读 `ip` / `ua`，300 万行的表里这部分回表 I/O 占了绝大部分时间；
  * 3.1.0 起建表脚本自带 `(time, ip)` 和 `(time, ip, ua)` 两个覆盖索引（PostgreSQL 实测计划变成 Index Only Scan，
    `Heap Fetches: 0`，读取的数据块从 838 降到 165）；
  * 3.0.x 建的老表没有这两个索引，插件不会自动去改已有的表，请照 `sql/` 下建表脚本里的两行
    `CREATE INDEX ... (time, ip)` / `(time, ip, ua)` 手动执行（记得把 `typecho_` 换成自己的表前缀）。
    PostgreSQL 建议加 `CONCURRENTLY` 以免阻塞读写，MySQL / SQLite 建索引期间该表写入会被阻塞，
    建议低峰期执行；300 万行实测每个索引约 6 秒；
  * 概览页改为**分段加载**：今日 / 昨日 / 总计 / 来源 / 饼图 / 当月各自一个请求，算完一段填一段。
    这解决的是一个死循环——整体请求超时 → 结果没算完 → 缓存建不起来 → 下次仍然是「第一次」。
    拆开之后每个请求都能跑完（300 万行实测最慢的一段 1.5 秒），缓存随之建立，之后整页热缓存约 0.1 秒；
  * 历史日期的统计结果长期缓存（过去的数据不会再变），当月图表按天推进，一次跑不完的话下次从缓存接着算。
    这部分依赖 Redis；没有配置 Redis 时分段照常工作，只是每次都要重算。
* v3.1.2 起插件配置可以放在文件里，随代码一起部署：
  * 启用插件时若存在 `config/current.yaml` 就按它设置，禁用插件时把当时的配置写回同一个文件，
    于是「禁用导出 → 换机器 / 重建容器 → 放回文件 → 启用导入」是闭合的，不必再到后台一项项填；
  * 文件里写了的项按文件走，**没写的项使用默认值**——加载一次相当于把插件配置整体替换成文件描述的样子；
  * 顶层为 `access:`，段内每行一个 `键: 值`，可用的键、默认值与完整示例见 [`config/README.md`](config/README.md)；
    布尔项写 `1`/`0` 或 `true`/`false` 都行，带引号的值一律按字面量处理（`dbName: "off"` 就是字符串 off）；
  * 只支持够用的 YAML 子集（标量、引号、注释），不依赖任何扩展；装了 PHP 的 `yaml` 扩展时会优先用它解析；
  * 文件含数据库密码、Redis 密码、IPinfo 令牌，写出时权限设为 `0600`，并在 `config/` 下放了
    `.htaccess` 与空 `index.html` 阻止 Web 直接下载。**Nginx 下这两个文件不起作用**，
    需要自行在站点配置里拒绝该目录；插件的 `.gitignore` 已包含 `config/current.yaml`，默认不会被提交；
  * 解析失败（语法错、权限不足）不会阻断启用，只在启用成功的提示里说明原因，沿用已有配置；
    写入失败（目录只读）也不影响禁用，只在提示里说明；
  * 建表在应用文件配置之后进行，因此文件里指定的独立数据库会立刻生效；
    若那个库连不上，启用会照常失败，且**不会**覆盖掉数据库里已有的配置。
* v3.1.3 起，配置里启用了 Redis 时，启用插件与在后台保存设置都会探测一次可用性：
  * Redis 只是加速器，**连不上不阻断启用**——缓存与写入队列自动降级，统计功能完整，
    只在提示里说明「已配置 Redis 但当前不可用」；恢复后无需改动，插件会自动重新连接；
  * 连接超时为 0.5 秒，并带熔断：连接失败后 30 秒内直接走降级路径，不再尝试连接。
    这一条是必要的——`Core` 在 `Widget\Archive::beforeRender` 里构造，
    而不可达的地址（防火墙丢包、DNS 黑洞、容器网络不通）会等满整个超时，
    没有熔断的话**每个前台请求都要白等一次**。实测不响应的地址：未熔断 502 ms，熔断后 0 ms；
  * 熔断状态需要跨请求保存（PHP 每个请求从干净状态开始），优先用 **APCu**（共享内存，自带 TTL），
    没装该扩展就退回临时目录下的标记文件（用 mtime 当时间戳）。
    **APCu 是可选依赖**，没有也不影响任何功能，只是少一层加速；
  * 标记文件放在临时目录下权限 0700 的专属子目录里，文件名带插件目录指纹，同机多站互不干扰；
  * 端口没人监听（连接被拒绝）是毫秒级返回，本来就无所谓；熔断针对的是「不响应」那一类。
* v3.1.5 起，写入队列围绕「一条访问日志不该无声消失」做了一轮加固：
  * 消息在 Redis 里经过三个列表：主队列 → `processing`（正在写库）→ 死信。
    消费者用一段 Lua 把消息**原子地**从主队列搬进 `processing`，不再「先读、写库、再按位置裁剪」——
    原来生产者在队列超过 20 万条时的裁剪一旦插在读与裁之间，消费者就会裁掉刚写进来、还没落库的消息；
  * 取走消息之后崩溃也不丢：那一批停在 `processing` 里，下次刷库开工前先把它捡回来；
  * 刷库锁改用随机 token，释放时用 Lua 比对归属，刷库期间每 10 秒续租一次，发现锁已易主立即停手；
    抢锁从页面渲染前推迟到 `shutdown` 真正开始刷库时。原来锁值是进程 PID、释放时直接 `DEL`，
    超时的旧消费者收尾时会删掉新消费者的锁，同一个队列上于是出现多个消费者；
  * 写不进数据库的消息进**死信队列**（`plugin:access:{指纹}:queue:dead`，上限 1 万条）并保留原始内容，
    而不是跟着整批一起删掉——原来一批 1000 条只要有 1 条写入成功，其余 999 条就没了；
  * 整批失败时先探活数据库，区分「数据库不可用」（保留重试）与「整批都是脏数据」（转入死信），
    队尾只剩一条写不进去的记录时不会再永久卡死队列；
  * 单次刷库的上限按**取出条数**而不是写入成功数计算，并加了 20 秒墙钟上限；
  * 落库之后按受影响的日期精确失效统计缓存。原来只更新时间戳，跨零点之后才把前一天的队列
    写进数据库的话，前一天的统计会带着错误数字挂到长缓存自然过期（最长 40 天）为止；
  * Redis 连接统一创建并设置**读写超时**（前台 3 秒，命令行 5 秒）。原来只有连接超时，
    TCP 连上但服务端不回话时会一直等到 PHP 的默认套接字超时；
    实测一个握手后不回话的地址耗时 60.06 秒，设了读超时之后按超时值返回；
  * 访问日志各字段按建表脚本的列宽截断，`cid` / `mid` 收进 `int unsigned` 范围；
    前端统计模式的 GIF 接口增加频率限制（每 IP 每分钟 60 次）。这个入口是匿名可达的，
    原来一条超长记录就能让批量 INSERT 失败并退化成上千次逐行 INSERT；
  * **停用插件不再连同未落库的数据一起删**：先循环刷库直到取空，仍有剩余且未勾选「数据清理」时，
    队列与死信原样保留，下次启用继续写入；在后台保存设置时，若改动会切换队列归属
    （Redis 地址或密码、关闭 Redis、关闭写入队列、更换统计数据库或表前缀），先用旧配置刷完再保存；
  * `tools/flush-queue.php` 在数据库不可用、刷库中断、锁易主或有消息转入死信时以退出码 1 结束
    （`--lenient` 可豁免最后一项），错误信息走 STDERR，新增 `--deadline` 参数，
    不再把 Redis 故障显示成「队列为空」后以成功退出。
* v3.2.0 起数据表带有**结构版本号**，升级时自动改表：
  * 版本号记在 Typecho 主库的 options 里，按统计库分别登记，因此在多个统计库之间切换时
    每个库的结构版本都能对上号；
  * 启用插件、或在后台保存一次设置时，若发现版本与代码不一致就自动执行升级
    （`ALTER TABLE` 加列、补索引），升到一半失败会停在最后一个成功的步骤上，下次接着来；
  * 这个版本号**只在表结构真正变化时**才跟着插件版本走，其余发布保持不动 ——
    否则绝大多数版本都要白跑一遍升级检查。当前值为 `3.2.2`；
  * 从 3.1.x 升级上来只需照常「禁用 → 启用」一次；只改了插件文件还没重新启用也不要紧，
    此时写入会自动摘掉新列继续进行（只是这段时间没有幂等保护），不会因为缺列而整批写失败。
* v3.2.0 起写入具备**幂等性**，队列重放不再产生重复记录：
  * 数据表新增 `event_id` 列与唯一索引，每条访问日志在**入队时**生成一个 32 位标识，
    重试时沿用同一个值（放到落库时再生成的话，每次重试都是一条「新」记录，唯一索引形同虚设）；
  * 标识的前 16 位十六进制包含毫秒时间戳和 16 位随机数，后 16 位也随机，因此按毫秒聚簇，
    唯一索引的写入集中在 B+ 树右端附近；同一毫秒内仍是随机顺序；
  * 队列做的是「至少一次」投递 —— 写库成功但从 `processing` 确认之前进程被杀，
    下一轮会把同一批再写一遍。有了唯一索引，重复的那次被数据库挡下，结果等同于「恰好一次」；
  * 写入改为「唯一冲突即跳过」：MySQL 用 `ON DUPLICATE KEY UPDATE`，
    PostgreSQL 用 `ON CONFLICT DO NOTHING`，SQLite 用 `INSERT OR IGNORE`。
    MySQL 特意**不用** `INSERT IGNORE`——它连字段超长这类数据错误也一并吞掉，
    而死信队列正是靠「数据库明确拒绝」来把脏数据挑出来的；
  * 存量数据的 `event_id` 保持 `NULL`，三种数据库的唯一索引都允许多个 `NULL`，
    老数据不受影响，只是那部分不具备幂等能力。
* v3.1.5 修复了前端统计模式的条件写反：`writeType=0`（前端）时 GIF 接口并不记录日志，
  而 `writeType=1`（后端）时该接口仍可被匿名调用重复写入。使用前端统计的站点请升级。

### 功能亮点

- 展示 PV/UV 及更多信息
- 自动忽略管理员登录及访问日志
- 支持显示 referer 来源信息并且以其进行排序
- 可设置禁用插件时清空日志
- 使用较精准的在线地址分析接口（有主备双接口）
- 支持后端/前端两种方式写入日志
- 支持根据 IP 、文章、标题、路由等进行分类排序日志
- 支持 MySQL / MariaDB、SQLite 和 PostgreSQL
